# Phase 2 step 0: why model JSON fails to parse (2026-10-21)

One diagnostic run with the step 0 logging (commit `0c42fb1`): cold launch, Health Scan IMG_9596,
Insights Generate. Release build, `vision_tokens=140`, `verbose=true`. Raw log:
`~/Gemma4Good/bench-logs/phase2-diag.log` (not in git).

## Parse failures

4 failures, all `invalid_json`. No response hit `max_tokens` (`hit_max_tokens=false` on all 5
inferences). No markdown fences, no prose around the JSON, no trailing commas.

| Source | JSONSerialization error | Defect in the model output |
|---|---|---|
| `health_vision` | Badly formed array around line 69, column 2 | `evidenceTrace` array closed with `}` instead of `]` |
| `health_vision_repair` | No value for key in object around line 3, column 71 | 8/8 metric rows have a corrupted key/value separator: `"normalRange} < 200"`, `"normalRange">= 40"` |
| `health_ocr_text` | Unexpected end of file around line 1, column 887 | Final `}` missing. `extractJSONObject` (first `{` to last `}`) then cut off the `evidenceTrace` tail, so the candidate was even shorter (885 of 1,160 chars) |
| `insights` (1st attempt) | Unescaped control character around line 9, column 279 | One string missing its closing `"` before a newline, and two arrays (`actions`) closed with `}` instead of `]` |

The defects are structural: wrong closing bracket, missing closing quote, missing final brace.

## A bracket-balancing pass would have rescued 3 of 4

Prototype (Python, offline on the logged text): scan from the first `{`, track a bracket stack and
string state; close a string at a raw newline, replace a mismatched closer with the expected one,
append missing closers at the end.

| Source | Result after the pass |
|---|---|
| `health_vision` | parses, 8 metrics |
| `health_vision_repair` | still fails (separator corruption is not a bracket problem) |
| `health_ocr_text` | parses, 8 metrics |
| `insights` | parses, 2 findings |

Prototype only; not yet implemented in Swift or measured on device.

## Implications for step 1

- A Swift bracket-balancing pass before `JSONSerialization` removes the Insights retry (235 s in this
  run) and the health repair inference (147 s), whose own output was also unparseable.
- Fixing the JSON alone would make the scan return the vision result, which here was 7/8 wrong.
  Step 1 (JSON tolerance) must ship together with step 2 (vision values checked against OCR text),
  otherwise accuracy gets worse.
- `extractJSONObject` should not cut at the last `}`; the balancing pass replaces it.
